# Elitea Compose

Deploy the Elitea platform on a single host with Docker Compose.
One script checks your machine, installs what is missing, renders the configuration with Terraform and starts everything.

- **Quick start** – one command, zero questions, everything on.
- **Custom** – the same script, with a wizard for networking, TLS, SSO, external databases, plugins and more.

Supported hosts: **Ubuntu, Debian, RHEL family (RHEL / Rocky / Alma / CentOS / Fedora) and macOS** (Docker Desktop).

## Quick start

### What you need

| | |
|---|---|
| CPU | **6 vCPU** minimum, 12 vCPU recommended |
| RAM | **8 GB** minimum, 16 GB recommended |
| Disk | **30 GB** free (the script checks this) |
| Network | Internet access to pull container images and download Terraform |
| Rights | `sudo` only if Docker / `make` / `unzip` have to be installed. If they are already there, no root is needed |
| Docker | Not required up front – `start.sh` offers to install it (Linux) |

> **Note:** the first startup bootstraps the platform and can take up to 15 minutes, depending on your internet connection and system performance.

### 1. Run the script

```sh
git clone <this-repository-url> elitea_compose
cd elitea_compose
bash start.sh
```

### 2. Press Enter

```
Setup mode:
  1 - Quick start (defaults, all optional plugins on, passwords autogenerated)
  2 - Customize
Choose [default: 1]:
```

Choose **1** (or just press Enter). The script then:

1. Detects your OS and prints a prerequisite report:
   ```
   make installed .............................. ✓ GNU Make 4.3
   docker installed ............................ ✓ Docker version 29.x
   docker compose installed .................... ✓ 5.x
   terraform installed ......................... ✓ Terraform v1.x
   host address ............................... ✓ 192.168.1.124
   port 80 .................................... ✓ free
   disk space ................................. ✓ 914G free (need 30G)
   ```
   Anything missing is installed after your confirmation (`yes` by default).
2. Generates passwords and saves every answer to `inputs.env` (mode `600`).
3. Runs `make init`, `make apply` and `make up` for you.

When it finishes you will see:

```
ELITEA is starting: http://192.168.1.124:80  (admin password is in inputs.env)
```

### 3. Log in

Open the printed URL. Login: **`admin`**. The password is the `ADMIN_PASSWORD` line in `inputs.env`.
First start downloads images and initialises the databases – give it a few minutes.

> **Open Elitea by exactly the address that was printed.**
> The address is the Elitea *server host* (`APP_HOST`). If you open the machine by another IP, DNS name or by `localhost`, the page will not work. See [Changing the address](#changing-the-address-or-redeploying).

### What Quick start deploys

| Item | Value |
|------|-------|
| Address (`APP_HOST`) | Primary IPv4 of the host, `localhost` if it cannot be detected |
| HTTP port | `80`; automatically `8080` if port 80 is busy or blocked (rootless Docker) – you get a note at the end |
| TLS | Off (plain HTTP) |
| PostgreSQL (pgvector) and Redis | Local containers with generated passwords |
| Login | Built-in form login, user `admin` |
| Plugins | DeepWiki, ImageGen, Inventory – **on** |
| Mesh, tracing, auto config | **on** |
| MCP servers (Grafana, Azure DevOps), internal OTEL collector | off |

Want something different? Use [Custom](#custom-setup).

### Everyday commands

```sh
docker compose ps                    # what is running
docker compose logs -f pylon_main    # follow one service (pylon_auth, pylon_indexer, ...)
make stop                            # stop containers, keep everything
make up                              # start again
make down                            # remove containers and network, data volumes are kept
```

### Changing the address or redeploying

Run the script again. If Elitea is already deployed in this directory it offers to stop it (`docker compose down`, **data is kept**) and redeploys with the new settings:

```sh
APP_HOST=elitea.example.com bash start.sh
```

On a re-run Quick start **reuses the passwords from `inputs.env`**, so the existing database and Redis volumes keep working.

`APP_HOST` must be one concrete IP or DNS name. Wildcards such as `*` are not supported. For several public names put a reverse proxy in front that forwards the `Host` header you configured.

### Troubleshooting

| Symptom | Cause / fix |
|---------|-------------|
| Page does not open by IP, works by `localhost` (or vice versa) | `APP_HOST` differs from the address in the browser. Re-run with `APP_HOST=<address> bash start.sh` |
| `all predefined address pools have been fully subnetted` | Your host routes (typically a VPN with `0.0.0.0/1` + `128.0.0.0/1`) overlap every default Docker network range. Disconnect the VPN or use split tunnelling, then run `make up` again |
| `address already in use` | Another service owns the port. Re-run the script (it falls back to 8080) or choose a port in Custom mode |
| `unable to open database file` in a pylon container | The `pylon_*` directories are not writable for the container. Containers run with `DAC_OVERRIDE` for this; make sure you generated the compose file with the current templates (`make apply`) and recreate the containers (`docker compose up -d --force-recreate`) |
| `make full_clean` cannot remove files | Files created by containers belong to root. The clean targets remove them through a throw-away container, so Docker must be running |
| Not enough disk space | Free up at least 30 GB (override the check with `FREE_SPACE_THRESHOLD=<GB>`) |

## Custom setup

Run `bash start.sh` and choose **2 – Customize**. Every question has a default, so you can press Enter for anything you do not need to change. At the end you can save all answers to `inputs.env` and deploy right away.

Legend for the *Recommendation* column: **prod** = what we advise for a long-lived installation, **eval** = what is fine for a trial or a local test.

### Network and access

| Setting | Wizard prompt | Variable | Default | Recommendation |
|---------|---------------|----------|---------|----------------|
| HTTP port | `HTTP port` | `HTTP_HOST_PORT` | `80` (`8080` if 80 unavailable) | Keep `80`/`443` on a dedicated host. Use a high port if something else already listens there |
| TLS at a load balancer | `External LB has TLS?` | `LB_HTTPS` | `no` | **prod:** terminate TLS at a load balancer / ingress and answer `yes`. Elitea then generates `https://` URLs |
| TLS in Elitea | `ELITEA will serve HTTPS itself…` | `SELF_HTTPS` | `no` | Use when there is no load balancer. Put `server.crt` and `server.key` into `cacerts/` **before** `make up`. See [Certificates](#certificates-tls-and-custom-ca) |
| HTTPS port | `HTTPS port` | `HTTPS_HOST_PORT` | `443` | Keep default |
| Server host | `Enter host IP address or DNS` | `APP_HOST` | detected host IP | **prod:** a stable DNS name (an IP changes with DHCP). Must equal what users type in the browser. One name only, no wildcards |
| Corporate proxy | `Use internal company proxy?` | `PROXY_ENABLED`, `PROXY_ENABLED_HTTP`, `PROXY_ENABLED_HTTPS`, `PROXY_ENABLED_NO_PROXY` | `no` | Enable only behind an egress proxy. Always add your internal domains and the Docker service names to `no_proxy` |
| Custom CA | `Use custom external CA?` | `CA_ENABLED` | `no` | Needed when Elitea talks to services signed by a private CA (SSO, proxy, Git). Put the CA certificate into `cacerts/ca.crt` **before** `make up`. See [Certificates](#certificates-tls-and-custom-ca) |

### Authentication (SSO)

| Setting | Variable | Default | Recommendation |
|---------|----------|---------|----------------|
| Use SSO | `SSO_ENABLED` | `no` | **prod:** enable, so users sign in with your identity provider. Form login (`admin` + password) is fine for **eval** |
| SSO mode | `SSO_MODE` | `form` | `oidc` or `saml` depending on your IdP |
| OIDC | `OIDC_AUTHORIZATION_ENDPOINT`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`, `OIDC_TOKEN_ENDPOINT`, `OIDC_USERINFO_ENDPOINT`, `OIDC_METADATA_ENDPOINT`, `OIDC_END_SESSION_ENDPOINT`, `OIDC_URL_MODE` | – / `external` | Copy the endpoints from your IdP's discovery document. Register the redirect URL under your `APP_HOST` |
| SAML | `SAML_AUTHN_DESTINATION`, `SAML_LOGOUT_DESTINATION`, `SAML_SP_KEY`, `SAML_SP_CERT`, `SAML_IDP_METADATA`, `SAML_IDP_CERT`, `SAML_ISSUER` | – | Prefer the IdP **metadata URL** over pasting certificates (easier rotation) |
| Allowed domains | `ALLOWED_DOMAINS` | `centry.user` | List only the e-mail domains that may sign in. `centry.user` is always included |

### Versions

| Setting | Variable | Default | Recommendation |
|---------|----------|---------|----------------|
| Pylon version | `PYLON_VER` | `1.2.28` | Keep the default. **prod:** pin explicitly and upgrade deliberately |
| Elitea release | `ELITEA_RELEASE` | `2.0.7` (also `2.0.6`) | Pin; never use a floating tag in production |
| Pylon tools image | `TOOLS_ENABLED` | `no` | Use the Pylon *tools* image variant. Leave `no` unless you need it |
| Elitea repository | `ELITEA_REMOTE_REPO` | `1` (standard) | `2` only if your organisation runs an internal mirror |
| pgvector image | `PG_VECTOR_VER` / `PG_VECTOR_VERSION` | `0.8.7-pg18-trixie` | Keep. Changing the PostgreSQL **major** version of an existing volume needs a dump/restore |
| Redis image | `REDIS_VER` | `8.10.3-alpine` | Keep |

### Database and cache

| Setting | Wizard prompt | Variable | Default | Recommendation |
|---------|---------------|----------|---------|----------------|
| External PostgreSQL | `Would you use external PGSQL service?` | `EXTERNAL_PGSQL_SVC_ENABLED`, `PGSQL_HOST`, `PGSQL_PORT`, `PGSQL_USER`, `PGSQL_DB` | `no` (local container) | **prod:** a managed or dedicated PostgreSQL with backups. The `pgvector` extension must be available |
| Managed PostgreSQL in cloud | `PGSQL in Cloud, skip creating PG Vector` | `PG_CLOUD` | `no` | Answer `yes` for cloud services (e.g. Azure) where the extension is enabled by the provider |
| Local DB user / name | `input PGSQL user / db` | `PGSQL_USER`, `PGSQL_DB` | `eliteausr` / `eliteadb` | Keep |
| Custom PostgreSQL config | `Use PGSQL custom config?` | `PG_CUSTOM_CONFIG_ENABLED` | `no` | Mounts your own `postgresql.conf` / `pg_hba.conf`. Tune only if you know the workload |
| External Redis | `Would you use external REDIS service?` | `EXTERNAL_REDIS_SVC_ENABLED`, `REDIS_HOST`, `REDIS_PORT` | `no` (local container) | **prod:** managed Redis or a dedicated instance with persistence |
| Redis TLS / AWS | `Enable REDIS SSL`, `Redis in AWS` | `REDIS_SSL`, `AWS_REDIS` | `no` / `no` | Enable SSL for any Redis reachable over a network you do not fully control |

Local PostgreSQL and Redis keep their data in Docker named volumes, which survive `make down`. Back them up before upgrades.

### Runtime features

| Setting | Variable | Default | Recommendation |
|---------|----------|---------|----------------|
| Auto config | `AUTOCREATE_DB` | `yes` | Creates the databases on first start. Keep `yes` unless an administrator pre-creates them (then also use an external DB) |
| Mesh | `MESH_ENABLED` | `yes` | Keep |
| Tracing | `TRACING_ENABLED` | `yes` | Keep; disable only if you do not run a collector and want less noise |
| Internal OTEL collector | `INTERNAL_OTPL_ENABLED` | `no` | Enable when you have no OpenTelemetry collector of your own |

### Optional plugin containers

Pick numbers separated by spaces (`1 3`), or `4` for all. Default in **Custom**: none; in **Quick start**: 1–3.

| # | Plugin | Variable | Container |
|---|--------|----------|-----------|
| 1 | DeepWiki | `DEEPWIKI_PLUGIN_ENABLED` | `pylon_deepwiki` |
| 2 | ImageGen | `IMAGEGEN_PLUGIN_ENABLED` | `pylon_imagegen` |
| 3 | Inventory | `INVENTORY_PLUGIN_ENABLED` | `pylon_inventory` |

Enable only what you use; each plugin is one more container to run and patch.

### Optional MCP servers

| # | Server | Key variables | Recommendation |
|---|--------|---------------|----------------|
| 1 | Grafana MCP | `GRAFANA_MCP_ENABLED`, `GRAFANA_URL`, `GRAFANA_SERVICE_ACCOUNT_TOKEN`, `GRAFANA_ORG_ID` | Use a **service account with a viewer role**. Keep *Disable Grafana write operations* = `yes`. Restrict `GRAFANA_MCP_ALLOWED_HOSTS` / `GRAFANA_MCP_ALLOWED_ORIGINS` instead of leaving `*` where possible |
| 2 | Azure DevOps MCP | `ADO_MCP_ENABLED`, `ADO_MCP_ORGANIZATION`, `ADO_MCP_PERSONAL_ACCESS_TOKEN`, `ADO_MCP_API_KEY` | Use a PAT with the minimum scopes, and a random client API key. See [Azure DevOps MCP](#azure-devops-mcp) |

### Credentials and secrets

| Setting | Variable | Default | Recommendation |
|---------|----------|---------|----------------|
| Admin password | `ADMIN_PASSWORD` | generated | Leave empty to generate, or set a strong one |
| Redis / PostgreSQL passwords | `REDIS_PASSWORD`, `PGSQL_PASSWORD` | generated | Leave empty to generate. Changing them later requires re-initialising the matching volume |
| Application secrets | `APP_AUTH_SECRET`, `APP_MAIN_SECRET`, `MASTER_KEY` | generated | Leave empty to generate. `MASTER_KEY` encrypts stored secrets – **back it up**; losing it makes them unreadable |
| HMAC keys | `EVENT_HMAC_KEY`, `RPC_HMAC_KEY`, `EXPOSURE_HMAC_KEY`, `INDEXER_HMAC_KEY` | generated | Leave empty to generate |

`inputs.env` contains all of the above in plain text. It is created with mode `600` and is git-ignored. **Do not commit or share it**; move the secrets to your secret store for production.

### Saving and reusing answers

```sh
source inputs.env
make init && make apply && make up
```

You can also skip the wizard completely by exporting variables yourself. Every variable above is accepted by `make` and Terraform:

```sh
export APP_HOST=elitea.example.com DEEPWIKI_PLUGIN_ENABLED=true
make apply && make up
```

## Certificates (TLS and custom CA)

Both kinds of certificate live in the **same directory, `cacerts/`**, and are mounted read-only into the containers. Create the files **before** `make up` (or `bash start.sh`). The wizard only asks whether you need them; it does not create or validate the files.

| What you want | Wizard answer | Variable | File(s) in `cacerts/` | Who uses it |
|---------------|---------------|----------|-----------------------|-------------|
| Elitea serves **HTTPS itself** (no load balancer) | `External LB has TLS?` = `no`, `ELITEA will serve HTTPS itself…` = `yes` | `SELF_HTTPS=true` | `server.crt`, `server.key` | `pylon_main` (listens on `HTTPS_HOST_PORT`, default 443; plain HTTP is then **not** published) |
| TLS ends at a **load balancer / ingress** | `External LB has TLS?` = `yes` | `LB_HTTPS=true` | none – the certificate lives on the balancer | Elitea only builds `https://` URLs and trusts the forwarded protocol |
| Elitea must trust a **private / corporate CA** (SSO provider, Git, model endpoints, TLS-inspecting proxy…) | `Use custom external CA?` = `yes` | `CA_ENABLED=true` | `ca.crt` | All pylon services (`pylon_main`, `pylon_auth`, `pylon_indexer` and the enabled plugins) |

Notes:

- The same `ca.crt` is also referenced when the **corporate proxy** option is on (`PROXY_ENABLED=true`), so put your proxy's CA there too.
- Files must be **PEM**. `server.crt` should contain the full chain (server certificate first, then intermediates). `server.key` must be **unencrypted** – no passphrase is configured. `ca.crt` may hold several CA certificates concatenated.
- The certificate must be valid for the address users open, i.e. **`APP_HOST`**.
- Never commit certificates or keys to git.

Layout:

```text
cacerts/
├── ca.crt          # only with CA_ENABLED=true (or a proxy)
├── server.crt      # only with SELF_HTTPS=true
└── server.key      # only with SELF_HTTPS=true
```

**Trial with a self-signed certificate** (browsers will show a warning). Replace the name or IP with your `APP_HOST`:

```sh
openssl req -x509 -newkey rsa:4096 -nodes -days 365 \
  -keyout cacerts/server.key -out cacerts/server.crt \
  -subj "/CN=elitea.example.com" \
  -addext "subjectAltName=DNS:elitea.example.com,IP:192.168.1.124"
```

**Production:** use a certificate from your CA or Let's Encrypt, or – preferably – terminate TLS on a load balancer and answer `yes` to `External LB has TLS?`.

**Renewing a certificate:** replace the files and restart the service: `docker compose restart pylon_main`. When a CA changes, restart all pylon containers: `docker compose restart`.

## Azure DevOps MCP

Enable it in the wizard (MCP option `2`) or configure it directly:

```sh
export ADO_MCP_ENABLED=true
export ADO_MCP_ORGANIZATION=my-organization
export ADO_PAT=replace-with-your-raw-azure-devops-pat
export ADO_MCP_PERSONAL_ACCESS_TOKEN="$(printf ':%s' "$ADO_PAT" | base64 -w0)"
export ADO_MCP_API_KEY=replace-with-a-random-client-key
make apply
make up
```

The PAT is used for outbound Azure DevOps API requests; `ADO_MCP_PERSONAL_ACCESS_TOKEN` must be the base64 encoding of `:<raw-pat>`. On macOS use `base64 | tr -d '\n'` instead of `base64 -w0`. `ADO_MCP_API_KEY` protects inbound MCP requests from Elitea.

Configure the Elitea Remote MCP URL as `http://ado-mcp:3000` and paste this into the **Headers** field (leave OAuth client ID and secret empty):

```json
{ "Authorization": "Bearer <ADO_MCP_API_KEY>" }
```

For independently revocable keys use labelled API keys:

```sh
export ADO_MCP_LEGACY_API_KEY_ENABLED=false
export ADO_MCP_MULTIPLE_API_KEYS_ENABLED=true
export ADO_MCP_API_KEYS='{"alice":"key-a","automation":"key-b"}'
```

## Make targets

| Target | What it does |
|--------|--------------|
| `up` | Start all containers (checks free disk space on the first run) |
| `up_minimal` | Start only `pylon_main` and `pylon_auth` |
| `stop` | Stop containers |
| `down` | Remove containers and the network (volumes are kept) |
| `restart` | Recreate all containers |
| `init` | Initialise Terraform providers (first time only) |
| `plan` | Preview what Terraform will render |
| `apply` | Render `docker-compose.yml` and all service configs |
| `check_config` | Validate `envs/override.env` and `docker-compose.yml` |
| `get_tools` | Download Terraform (and ctop) into `~/.local/bin` |
| `prepare_ubuntu` / `prepare_rocky` | Host tuning, base packages and Docker install (Ubuntu/Debian · RHEL family) |
| `clean_images` | Remove the service images |
| `clean_volumes` | Remove the data volumes (asks first) |
| `clean_local_db` | Remove local `pylon.db` files (asks first) |
| `clean_cache` | Remove `plugins/`, `requirements/` and `cache/` of every pylon (asks first) |
| `clean_start` | `clean_cache` + `clean_local_db`, then start |
| `clean_tf` | Remove Terraform state and all rendered configs |
| `full_clean` | Wipe everything: DBs, cache, images, volumes, Terraform state, generated directories |

`full_clean` and `clean_volumes` **delete your data**. Everything under `docker-compose.yml`, `envs/override.env` and `pylon_*/` is generated by `make apply` – change the templates in `tmpl/`, never the generated files.

## How it works

```
start.sh            ← checks the host, asks (or not), writes inputs.env, runs make
Makefile            ← passes the settings to Terraform
tmpl/*.tf           ← Terraform
tmpl/tftemplates/   ← templates of docker-compose.yml, envs and pylon configs
        ↓ make apply
docker-compose.yml, envs/override.env, pylon_*/   ← generated (git-ignored)
```

Core services: `postgres` (pgvector), `redis`, `pylon_auth`, `pylon_main`, `pylon_indexer`. Optional: `pylon_deepwiki`, `pylon_imagegen`, `pylon_inventory`, `pylon_otpl`, `ado-mcp`, Grafana MCP.
